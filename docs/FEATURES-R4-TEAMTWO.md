### 6. onBackPressed migration (N-10) — ✅ MIGRATED
- The back logic is extracted verbatim into `handleBack(): Boolean` (true = handled in-app; false = let the system finish). Screen coverage is identical to Round 3, plus `"trash" -> Home`.
- **API 33+:** `onCreate` calls `registerPredictiveBackCallback()` **only when `Build.VERSION.SDK_INT >= 33`**; it registers an `android.window.OnBackInvokedCallback` via `onBackInvokedDispatcher` (PRIORITY_DEFAULT) that runs `if (!handleBack()) finish()`. Registration is wrapped in try/catch(Throwable) — on failure `backCallbackRegistered` stays false and the override below takes over. The registration lives in its own method that is never invoked below API 33, so the API-33 types are never touched on older devices (framework-only, no AndroidX).
- **API < 33:** the deprecated `onBackPressed()` override remains, now a three-line delegate: it returns immediately if `backCallbackRegistered` (belt-and-braces — when a callback is registered the system delivers Back to it and does not invoke the override, so there is no double-handling), otherwise `if (!handleBack()) super.onBackPressed()`.
- The migration **compiled cleanly** in framework-only style (the single remaining deprecation warning points at the `super.onBackPressed()` call inside the fallback override — expected and unavoidable while the <33 path exists). Runtime behaviour on a device cannot be exercised from this VM; the logic itself is unchanged from the verified Round 3 override, only its dispatch is new.

- **Where:** `showTrash()` (new screen), Home nav gains **"🗑 Trash"**, `UndoEntry.trashEntry` + `restoreViaTrash(e)` helper, all six `deleteXWithUndo` functions rewired. Back from Trash → Home; `refreshCurrent` knows the `"trash"` screen.
- **Trash screen:** lists `Store.trash` **newest first** (Store appends newest last; the UI reverses). Each entry card: label, kind chip (`CHANNEL`/`PAGE`/`SCRIPT`/`IDEA`/`TASK`/`BLOCK`), "Deleted: yyyy-MM-dd HH:mm" (`fmtDayTime`). **Restore** → `Store.restoreFromTrash(id)` → persist + toast; on **false** the entry stays and a toast explains it couldn't be restored (e.g. an item with the same id exists). **Delete forever** → confirm dialog → `Store.permanentlyDeleteTrash(id)`. Header **"Empty trash"** → confirm dialog (states the count and that it cannot be undone) → `Store.emptyTrash()`. Empty state note when there are no entries. Restoring also clears any pending undo bar state only via Empty trash's `hideUndoBar()`; undo-bar timing/behaviour is otherwise identical for the user (6 s, same bar).
- **Delete-flow rewiring — ALL SIX entity types are trash-backed** (the brief's minimum was pages/channels/scripts; ideas/tasks/blocks are wired too):
  - `deleteChannelWithUndo` (after the disclosure confirm) → `deleteChannelToTrash`; `deletePageWithUndo` (after its disclosure confirm) → `deletePageToTrash`. On a returned entry, the `UndoEntry` carries only the `TrashEntry`; undo = `restoreFromTrash` (the full cascade restore, survivor links included — strictly the Round 3 snapshot semantics). **Fallback:** only if the ToTrash call returns null does the Round 3 `removeChannelCascade`/`removePageCascade` + snapshot-undo path run, exactly as before.
  - `deleteScriptWithUndo` / `deleteIdeaWithUndo` / `deleteTaskWithUndo` / `deleteBlockWithUndo` → the matching `deleteXToTrash`; on null, the plain `removeX` path runs as fallback. Undo restores via `restoreFromTrash` when an entry exists (else the legacy `restoreX`), and — per Team One's §7.2 contract — the existing `clearedLinkIds`/`clearedLinkIds2` relink loops and the `linkIdeaToScript` relink **still run** for singles, so other-side links cleaned by the delete come back exactly as in Round 3. Script/block draft-clearing (R2-N7) is unchanged.
- **Disclosure wording updated honestly:** channel dialog now ends *"…You can undo right after deleting, or restore it later from Trash."*; page dialog likewise (*"…unlinked, not deleted. You can undo right after deleting, or restore it later from Trash."*). The undo bar still works in both cases.
